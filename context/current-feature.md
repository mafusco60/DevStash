Hand-written migration `20260521062554_rename_user_verification_token_add_purpose` uses `ALTER TABLE RENAME` + `ALTER INDEX RENAME` + `ALTER TABLE RENAME CONSTRAINT` instead of drop-and-recreate so existing token rows survive the rename, then adds the `purpose` column with a `DEFAULT 'EMAIL_VERIFY'` for back-fill and drops the default so future inserts must specify purpose explicitly; new composite index on `(userId, purpose)`. `User.emailVerificationTokens` back-relation renamed to `User.verificationTokens`. (Prisma 7's auto-generated migration would drop the table — generated SQL had to be replaced entirely.) Migration applied to the Neon dev branch (`br-withered-tooth-apihj818`) — production untouched. New `src/lib/verification-tokens.ts` houses the shared token core (`hashToken`, `generateRawToken`, `issueToken({ userId, purpose, ttlMs })` doing the atomic `$transaction` of `deleteMany` + `create` scoped to userId+purpose, and `findToken({ rawToken, purpose })` doing read-only lookup returning `{ ok: true, tokenId, userId } | { ok: false, reason: 'invalid' | 'expired' }` with best-effort delete of expired rows). `src/lib/email-verification.ts` was refactored to delegate to that core while preserving its public API — `issueVerificationToken(userId)` and `consumeVerificationToken(rawToken)` keep their old shapes, `hashVerificationToken` is now a re-export of `hashToken`, and `consumeVerificationToken` builds on `findToken` then runs its own atomic transaction to set `User.emailVerified` and delete the token. All existing callers (`/api/auth/register`, `/api/auth/verify-email`, `/api/auth/resend-verification`) were untouched as a result; the only knock-on edits were `scripts/test-verify-flow.ts` and `scripts/cleanup-non-demo-users.ts` which both reference the Prisma delegate / relation name directly. New `src/lib/password-reset.ts` exports `PASSWORD_RESET_TOKEN_TTL_MS = 1h`, `issuePasswordResetToken`, `findPasswordResetToken`, and `sendPasswordResetEmail` (dark-themed HTML + plain-text, 1h expiry copy). New `POST /api/auth/forgot-password` always responds 200 (no enumeration), and only issues + sends when the user exists AND has a `password` set so OAuth-only accounts are silently no-op'd; send is wrapped in try/catch. New `POST /api/auth/reset-password` Zod-validates (`token`, `password` ≥ 8, matching `confirmPassword`), then runs a single `$transaction` of three operations: `user.update` to set the bcrypt hash (12 rounds), `user.updateMany` filtered on `emailVerified: null` to conditionally set `emailVerified = new Date()` only when previously unverified (prevents overwriting an existing verification timestamp), and `userVerificationToken.deleteMany` filtered by `userId` + `PASSWORD_RESET` purpose to clear every outstanding reset token for the user. Returns generic 400 `{ error: "…invalid|expired" }` with a `code` so the form can recover, field-shaped 400 on Zod failure (matches the existing register-route pattern using the deprecated `parsed.error.flatten().fieldErrors` — kept consistent with that file's style rather than chasing the deprecation hint). New `/forgot-password` page is a server component that redirects authenticated users to `/dashboard`, renders `ForgotPasswordForm` (client, colocated with the page per project convention — `src/components/auth/...` was in the spec but the codebase consistently colocates page-specific forms à la `SignInForm`/`RegisterForm`). The form runs client-side Zod, POSTs JSON to `/api/auth/forgot-password`, and on success swaps to a generic "if an account exists for &lt;email&gt;, a reset link is on its way" message (1h expiry copy). New `/reset-password` page is a server component that reads `searchParams.token`, does a read-only `findPasswordResetToken` lookup (does NOT consume — that happens on POST), and renders either a friendly "Reset link expired" / "Reset link invalid" state with a styled `<Link>` to `/forgot-password` (Base UI Button has no `asChild` — codebase pattern is a styled `<Link>` directly, copied from `/verify-email/result/page.tsx`), or `ResetPasswordForm` with the token threaded as a prop. The form runs client-side Zod (password ≥ 8 + match via `.refine`), POSTs JSON to `/api/auth/reset-password`, maps `body.issues` back onto field errors, and `router.push("/sign-in?reset=1")` on success. `/sign-in` page reads a new `reset` searchParam and renders an emerald `role="status"` confirmation banner when `?reset=1`; `SignInForm` got a `Forgot password?` link to the right of the Password label (`flex items-center justify-between` over the input). `npm run build` clean — 16 routes total (4 new from this feature: 2 pages + 2 API routes).
